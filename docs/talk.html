03驗證體系：讓 Agent 自己證明「它真的動了」

Code Review 沒有消失，而是被壓縮為「只審驗證產物」：操作影片、介面截圖、狀態機圖。

執行期驗證（Runtime Verification）
  • Feature Map 功能地圖：使用者視角的功能樹 —— 有哪些功能、怎麼點過去、什麼狀態算跑通。別讓 Agent 猜「左邊欄那個小按鈕」。
  • 自訂 CLI：把 Chrome DevTools Protocol 等操作包成可重用指令，省 Token，CLI 本身也能被測試。

形式化驗證 & 屬性測試
  • TLA+：跨裝置、多端通知等核心流程做狀態機模型檢測。
  • Lean：為自研虛擬捲動庫寫數學證明，確保無閃爍/抖動。
  • Bombadil（antithesishq/bombadil）：UI 屬性測試，自動探索介面邊界 Bug。

佐證：Cindy Sridharan 表示現在每天 70% Token 花在驗證，僅 20–30% 用於產生程式碼，半年前的翻車問題不再出現。

執行期驗證：Feature Map 搭配可重用 CLI

Feature Map 是一棵「使用者視角」的功能樹：每個功能怎麼點過去、什麼狀態才算跑通。Agent 改完 UI 後照著地圖、用 CLI 自己啟動 App 點一遍、截圖或錄影貼回 PR；人類先看證據，再決定要不要翻 diff。CLI 把 Chrome DevTools Protocol 等操作包成固定指令，比每次臨場寫腳本省 Token，而且 CLI 本身也能被測試。

形式化驗證詳解：TLA+ 狀態機建模與 Lean 程式碼證明

測試只檢查「有人想到要寫」的案例；形式化驗證檢查一個明確範圍內的每一種情況：模型裡所有步驟的先後順序、某個界限內的所有輸入，或是全部輸入。它用在 Bug 代價最高、但測試最難碰到的地方：兩個重疊的重試、寫到一半過期的鎖、亂序到達的狀態變更。

TLA+ 怎麼抓 Bug：反例路徑示意

TLA+ 不是跑你的程式，而是描述設計：有哪些狀態變數、有哪些動作可以發生、哪些條件（不變式）永遠不能被打破。模型檢測器 TLC 會窮舉所有動作的交錯順序；一旦打破不變式，就回報一條最短反例路徑。下圖用 pstack 指南中的例子「同一個 job 絕不能同時執行兩次」示意。

Lean：為虛擬捲動「證明」不閃爍

問題在哪

虛擬捲動只渲染可視範圍內的列。列高在渲染後才知道、或內容即時變化時，捲動位置需要重新計算；算錯一點點，畫面就會跳動或閃爍。這種錯誤跟「列數 × 列高變化 × 捲動位置」的組合有關，測試只能抽樣幾種。

Lean 做了什麼

把捲動位置計算寫成數學定義，對任意列數、任意列高更新證明不變式成立，例如「使用者正在看的錨點列，更新前後在螢幕上的位置不變」。證明一旦通過，就是對所有情況成立，而不是對測過的情況成立。

註：講者只說明「用 Lean 證明自研虛擬捲動庫不存在閃爍或抖動」，具體定理未公開，上述不變式為說明用的示意。

外迴圈：不要自動化一個壞迴圈

內迴圈產出的本來就是垃圾，接上自動觸發器只會用更貴的 Token 帳單批量生產更多垃圾。先依金字塔把內迴圈磨成高信任，再接 Grok Bot 外迴圈（X、Linear、Slack、Cron、監控告警）。
