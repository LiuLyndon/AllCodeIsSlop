網頁 / UI 改動 · 從「說過了」到「拿證據」

UI 驗證實作讓代理真的開瀏覽器、點過一遍、交出證據

把演講與 pstack 對網頁、UI 的要求整理成一條完整流程，並補上落地需要的設定與範例程式。原則只有一條：只要改動碰到 UI，「編譯過了」「單元測試通過」都不算完成，必須有實際操作的證據。

來源對照整體流程讓代理開瀏覽器證據與對照獨立盲測屬性測試Lint 護欄

00四個做法在來源中的位置

本頁把散在各處的內容合併成一條流程。下表標明哪些是來源原話、哪些是本站為了落地補上的延伸。

做法來源中怎麼寫本站詳述位置本頁延伸
1. 執行期驗證Feature Map＋CLI 自己啟動 App 點一遍；人只審影片、截圖、狀態機圖；bug fix 劇本「重現 → 根因 → 修復 → 附執行期證據」；原則 prove it works演講 › 驗證體系、pstack › 劇本可直接用的 Playwright 流程腳本、修前／修後對照、效能圖表、強制執行的 hook
2. 獨立盲測寫碼 Agent 嚴禁自審，每個 PR 派全新 Agent 實跑驗真（playbooks/shipping.md）pstack › 獨立驗收流水線不給 diff、只給 Feature Map 的「使用者視角」驗收提示詞
3. UI 屬性測試驗證方法表中一列：Bombadil，隨機產生大量輸入與操作序列，探索 UI 邊界演講 › 驗證方法表要檢查哪些不變式、怎麼把失敗序列固定成回歸測試、示意程式
4. Lint 護欄Dune 業務碼禁用 useEffect；1 個 setTimeout 五週變 183 個；Lint 規則 7 → 167；encode-lessons-in-structure演講 › 程式碼庫ESLint 設定範例（錯誤訊息附修正方式）

01整體流程：一個 UI 改動從派工到合入

階段 0 只做一次；階段 1–6 每個任務都走一遍；階段 7 讓同樣的錯不再出現第二次。

階段誰做產出沒有產出就…
0 搭環境（一次性）人＋Agent瀏覽器操作 CLI、Feature Map、視覺基準圖、Lint 基本盤、強制留證的 hook後面每一關都只能靠人肉點
1 派工人三行任務單：目標／完成判定標準／要看的實跑證據Agent 自己決定「怎樣算完成」
2 開發寫碼 AgentBug：先寫出能重現的操作流程；功能：先寫好驗收流程不准開始改程式
3 實跑留證寫碼 Agentevidence/<任務>/before（失敗）與 after（通過）：截圖、影片、trace、必要時效能圖hook 擋住 Agent，不准宣告完成
4 PR寫碼 Agent → 人PR 描述附證據；審查者先看影片／截圖再決定要不要翻 diffCI 擋下 UI 類 PR
5 屬性測試CI／每晚排程隨機操作序列下的不變式報告；失敗序列縮成最小重現失敗序列存成回歸測試後再修
6 獨立盲測全新 Agent（最好換模型）以使用者身分照 Feature Map 操作一遍的驗收報告＋證據＋PASS/FAIL退回階段 2
7 規則化人決定、Agent 寫新 Lint 規則或測試，錯誤訊息附「正確寫法」同一個錯會換個地方再長出來

02怎麼讓代理「真的」開瀏覽器、點過一遍

拆成三件事：給工具（它有能力操作）、給地圖（它知道要點哪裡、怎樣算成功）、給強制（沒有證據就不能說完成）。只寫在 AGENTS.md 裡的「請記得用瀏覽器測試」，就是演講裡說的「寫在文字裡、不寫進工具」，早晚會被跳過。

① 給工具：三種接法，擇一即可

A. 專案自帶 CLI（推薦，演講做法）
用 Playwright 或 Chrome DevTools Protocol 包成固定指令，所有 Agent、所有工具共用同一套。省 Token、可重跑、CLI 本身也能寫測試。下方有完整範例。
B. pstack 產生的 verify 技能
/pstack:setup-pstack 時答應產生 /create-verification-skill，會寫出 Launch → Doctor → Drive → Evidence → Cleanup 五段的 verify-<app> 技能。瀏覽器／Electron 操作可搭配 cursor-team-kit 的 control-ui。
C. 代理工具內建的瀏覽器
Claude Code 可接 Playwright MCP 或 Claude in Chrome；Cursor 有內建瀏覽器。上手最快，但每次臨場摸索、較耗 Token，也較難在 CI 重跑。適合先體驗，穩定後再收斂成 A。

A 的範例：一支「照流程點一遍並留證」的腳本

重點是流程寫成資料檔：同一個流程檔修之前跑一次、修之後再跑一次，就是「重現與對照」。Agent 不必每次重寫操作腳本，只要新增或修改流程檔。

npm i -D playwright && npx playwright install chromium
// scripts/ui-run.mjs
// 用法：node scripts/ui-run.mjs flows/settings-save.json evidence/settings-save/after
import { chromium } from 'playwright';
import { mkdir, readFile, writeFile } from 'node:fs/promises';

const [flowPath, outDir = 'evidence/latest'] = process.argv.slice(2);
const flow = JSON.parse(await readFile(flowPath, 'utf8'));
await mkdir(outDir, { recursive: true });

const browser = await chromium.launch();
const context = await browser.newContext({ recordVideo: { dir: outDir } });
await context.tracing.start({ screenshots: true, snapshots: true });
const page = await context.newPage();

const errors = [];
page.on('pageerror', (e) => errors.push(`pageerror: ${e.message}`));
page.on('console', (m) => m.type() === 'error' && errors.push(`console: ${m.text()}`));

const log = [];
try {
  for (const [i, s] of flow.steps.entries()) {
    log.push({ i, ...s });
    if (s.goto) await page.goto(new URL(s.goto, flow.baseURL).href);
    if (s.click) await page.getByRole(s.click.role, { name: s.click.name }).click();
    if (s.fill) await page.getByLabel(s.fill.label).fill(s.fill.value);
    if (s.press) await page.keyboard.press(s.press);
    if (s.expectText) await page.getByText(s.expectText).first().waitFor({ timeout: 5000 });
    if (s.screenshot) await page.screenshot({ path: `${outDir}/${String(i).padStart(2, '0')}-${s.screenshot}.png`, fullPage: true });
  }
} catch (e) {
  errors.push(`step failed: ${e.message.split('\n')[0]}`);
  await page.screenshot({ path: `${outDir}/failure.png`, fullPage: true }).catch(() => {});
}

await context.tracing.stop({ path: `${outDir}/trace.zip` });
await context.close();               // 關閉後影片才會寫入 outDir
await browser.close();

const result = { flow: flowPath, ok: errors.length === 0, errors, steps: log.length, at: new Date().toISOString() };
await writeFile(`${outDir}/result.json`, JSON.stringify(result, null, 2));
console.log(JSON.stringify(result, null, 2));
process.exit(result.ok ? 0 : 1);
// flows/settings-save.json —— 同時也是 Feature Map 裡「怎麼到達、什麼算成功」的可執行版本
{
  "baseURL": "http://localhost:5173",
  "steps": [
    { "goto": "/" },
    { "click": { "role": "button", "name": "Settings" } },
    { "fill": { "label": "Display name", "value": "Poteto" } },
    { "click": { "role": "button", "name": "Save" } },
    { "expectText": "Saved" },
    { "screenshot": "saved" }
  ]
}

用 getByRole／getByLabel 以無障礙名稱定位（對應演講的 app aria-click --accessible-name），比 CSS selector 穩定，也順便逼出可及性問題。失敗時看 npx playwright show-trace evidence/…/trace.zip。

## UI 驗證
- 改到 src/** 的 .tsx/.css → 先啟動 `npm run dev`，再用 `node scripts/ui-run.mjs <flow> <outDir>`
- 功能與流程對照：features/README.md
- 修 Bug：先跑一次存到 evidence/<task>/before（必須失敗），修好再存到 evidence/<task>/after（必須通過）
- 沒有 evidence 就不算完成（hook 會擋）

③ 給強制：沒有證據，Agent 不能宣告完成

這是「錯誤規則化」的同一個精神：不靠提醒，靠機器擋。兩道關卡：本機用代理工具的 hook，遠端用 CI。

本機：Claude Code 的 Stop hook
Agent 想結束回合時執行；若改了 UI 檔案卻沒有比改動更新、而且通過的 result.json，就以 exit code 2 擋下，並把原因回傳給 Agent，讓它自己補跑。Cursor 等工具也有類似的 hook 機制。
CI：PR 檢查
PR 改到 UI 路徑時，CI 自己再跑一次所有相關流程（不信任本機的結果），並把截圖、影片、trace 上傳成 artifact，連結貼回 PR。
// .claude/settings.json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "node scripts/require-ui-evidence.mjs" } ] }
    ]
  }
}
// scripts/require-ui-evidence.mjs
import { execSync } from 'node:child_process';
import { statSync, readFileSync, existsSync, globSync } from 'node:fs';   // globSync：Node 22+

const input = JSON.parse(readFileSync(0, 'utf8') || '{}');
if (input.stop_hook_active) process.exit(0);          // 已被擋過一次，避免無限迴圈

const sh = (c) => execSync(c, { encoding: 'utf8' }).split('\n').filter(Boolean);
const changed = [...sh('git diff --name-only HEAD'), ...sh('git ls-files --others --exclude-standard')];
const ui = changed.filter((f) => /^src\/.*\.(tsx|jsx|css|scss|html)$/.test(f) && existsSync(f));
if (ui.length === 0) process.exit(0);

const newestChange = Math.max(...ui.map((f) => statSync(f).mtimeMs));
const fresh = globSync('evidence/**/result.json')
  .map((f) => ({ f, t: statSync(f).mtimeMs, r: JSON.parse(readFileSync(f, 'utf8')) }))
  .filter((x) => x.t > newestChange && x.r.ok);

if (fresh.length === 0) {
  console.error([
    '你改了 UI 檔案，但沒有比改動更新、且通過的操作證據：',
    ...ui.map((f) => `  - ${f}`),
    '請啟動 App，用 node scripts/ui-run.mjs <flow> evidence/<task>/after 跑相關流程；',
    '若是修 Bug，還要附上修之前失敗的 evidence/<task>/before。',
  ].join('\n'));
  process.exit(2);                                    // 2 = 擋下並把 stderr 交給 Agent
}
# .github/workflows/ui-evidence.yml（節錄）
on: pull_request
jobs:
  ui:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci && npx playwright install --with-deps chromium
      - run: npm run build && (npm run preview &) && npx wait-on http://localhost:4173
      - run: for f in flows/*.json; do node scripts/ui-run.mjs "$f" "evidence/ci/$(basename "$f" .json)" || exit 1; done
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: ui-evidence, path: evidence/ci }

以上為本站依演講精神寫的示意設定，路徑與埠號請依專案調整；CI 範例中的 baseURL 需與 preview 埠一致（可在流程檔外以環境變數覆寫）。

03證據規格：重現與對照

修 Bug 的固定動作
  1. 寫一個流程檔，最後一步斷言「正確行為」。
  2. 在未修改的程式上跑 → 存到 before/，必須失敗。不失敗代表沒重現到，不准開始修。
  3. 追根因、修。禁止加 setTimeout、重試、吞錯誤來讓它「看起來好了」。
  4. 同一個流程檔再跑 → 存到 after/，必須通過。
  5. 把這個流程檔留在 flows/，從此成為回歸測試。
PR 描述模板 
## 證據
| | 修前 | 修後 |
|---|---|---|
| 流程 | flows/settings-save.json | 同左 |
| 結果 | ❌ step 4: "Saved" 未出現 | ✅ 6/6 |
| 截圖 | before/failure.png | after/05-saved.png |
| 影片 | before/*.webm | after/*.webm |

視覺比對：與 baseline 差異 0 張（或列出預期內差異）
效能（若相關）：互動延遲 / 長任務 前後對照圖
視覺回歸
改動前先拍一輪基準圖（pstack decisions.tsv 範例：「存下 120 張基準圖」），之後用 expect(page).toHaveScreenshot() 或像素比對找出跑版、閃爍。差異圖直接附在 PR。
效能圖表（本站延伸）
來源只寫到影片、截圖、狀態機圖。若改動涉及效能，可用 Playwright 的 tracing 或 Chrome Performance 記錄修前修後的長任務、版面重排次數，輸出成圖表附上。

04獨立盲測：換一個沒寫過這段程式的 Agent

pstack 的規定是「寫碼 Agent 嚴禁自審，verdict 必須來自沒寫這段程式的 Agent」。寫碼的 Agent 只會去測它以為自己寫對的地方，所以驗收者不給 diff、不給寫碼過程，只給使用者會知道的東西。

怎麼派
  • 開一個全新對話或子 Agent，最好換一個模型（異質模型，盲區不重疊）。
  • 只給：Feature Map、這次改動的使用者描述、可以用的 CLI。
  • 不給：diff、原始任務對話、寫碼 Agent 的自我評估。
  • 要求它除了「快樂路徑」，還要刻意亂操作：連點、返回、重新整理、空值、超長輸入、窄螢幕。
驗收提示詞範本 
你是第一次使用這個產品的使用者，也是驗收員。
你看不到程式碼，只能透過 scripts/ui-run.mjs 或瀏覽器操作。
功能說明：features/settings.md
本次改動（使用者角度）：「設定頁的顯示名稱現在可以儲存」
1. 照功能說明走完主要流程，每一步截圖。
2. 再嘗試 5 種一般使用者可能做的奇怪操作。
3. 輸出：PASS / FAIL、每個問題的重現步驟與證據路徑。
不要提出修改程式的建議，只回報你看到的行為。

每個窄 PR 都派一個驗收員，只合入從棧底開始連續 PASS 的 PR（詳見 pstack › 窄 PR 棧與獨立驗收流水線）。盲測抓到的問題要轉成新的 flows/*.json。

05UI 屬性測試：隨機狀態與邊界轟炸

E2E 只測「有人想到要寫」的路徑。屬性測試反過來：先寫下不管怎麼操作都必須成立的規則（性質），再讓工具自動產生大量隨機的操作順序與輸入去試著打破它。演講中 Grok Bot 團隊使用 Antithesis 的 Bombadil（antithesishq/bombadil）做這件事。

常用的 UI 不變式
  • 任何操作序列後，頁面都不會出現未處理的例外或 console error。
  • 不會卡死：每個動作後，介面在 N 毫秒內回到可互動狀態。
  • 狀態一致：畫面顯示的數量 = 資料層的數量（例如購物車徽章 = 列表項數）。
  • 可逆：開啟後關閉對話框，焦點與捲動位置回到原處。
  • 載入中與錯誤狀態最終一定會結束，不會永遠轉圈。
流程
  1. 從 Feature Map 挑出核心頁面，列出可執行的動作集合。
  2. 寫 3–5 條不變式，先在一個故意改壞的版本上確認會報錯（同 pstack 對形式化驗證技能的要求）。
  3. 放進 CI 或每晚排程，固定隨機種子以便重現。
  4. 找到失敗 → 工具縮小成最短操作序列 → 存成 flows/*.json 回歸測試 → 再修。

沒有導入 Bombadil 時，也可以用 fast-check 的指令模型搭配 Playwright 做出同樣的效果（以下為示意）：

// tests/cart.property.spec.ts（示意）
import { test } from '@playwright/test';
import fc from 'fast-check';

const actions = fc.array(fc.oneof(
  fc.constant({ do: 'add' }),
  fc.constant({ do: 'remove' }),
  fc.constant({ do: 'reload' }),
  fc.constant({ do: 'back' }),
  fc.string({ maxLength: 200 }).map((q) => ({ do: 'search', q })),
), { maxLength: 30 });

test('任何操作順序下，購物車徽章都等於列表項數，且沒有錯誤', async ({ page }) => {
  await fc.assert(fc.asyncProperty(actions, async (seq) => {
    const errors: string[] = [];
    page.removeAllListeners('pageerror');
    page.on('pageerror', (e) => errors.push(e.message));
    await page.goto('/shop');
    for (const a of seq) {
      if (a.do === 'add') await page.getByRole('button', { name: 'Add to cart' }).first().click();
      if (a.do === 'remove') await page.getByRole('button', { name: 'Remove' }).first().click().catch(() => {});
      if (a.do === 'reload') await page.reload();
      if (a.do === 'back') await page.goBack().catch(() => {});
      if (a.do === 'search') await page.getByRole('searchbox').fill(a.q);
    }
    await page.goto('/cart');
    const badge = Number(await page.getByTestId('cart-badge').textContent());
    const rows = await page.getByRole('listitem').count();
    return errors.length === 0 && badge === rows;
  }), { numRuns: 50, seed: Number(process.env.SEED ?? Date.now()) });
});

06Lint 護欄：禁用高風險寫法，錯誤訊息就是規則

演講的兩個 UI 相關教訓：useEffect 需要「PhD 級直覺」，Agent 最不擅長，所以 Dune 只在框架底層使用、業務碼禁用；為了修閃爍塞進去的 1 個 setTimeout，五週後被複製成 183 個。兩者都寫成 Lint，而不是寫在 AGENTS.md。

// eslint.config.js（節錄，示意）
const NO_EFFECT = '業務碼禁用 useEffect。資料請用 src/framework/hooks 的 useQuery；'
  + '訂閱外部來源用 useSubscription；由事件觸發的邏輯直接寫在事件處理函式裡。';
const NO_TIMER = '禁止用 setTimeout 修時序或畫面閃爍。請找出狀態更新的真正順序：'
  + '需要等 DOM 就用 ref callback；需要等資料就用 loading 狀態；動畫用 CSS transition。';

export default [
  {
    files: ['src/features/**/*.{ts,tsx}', 'src/pages/**/*.{ts,tsx}'],
    rules: {
      'no-restricted-imports': ['error', { paths: [
        { name: 'react', importNames: ['useEffect', 'useLayoutEffect'], message: NO_EFFECT },
      ] }],
      'no-restricted-syntax': ['error',
        { selector: "CallExpression[callee.property.name=/^use(Layout)?Effect$/]", message: NO_EFFECT },
        { selector: "CallExpression[callee.name='setTimeout']", message: NO_TIMER },
        { selector: "CallExpression[callee.property.name='setTimeout']", message: NO_TIMER },
      ],
    },
  },
  // src/framework/** 不套用：底層框架可以使用，並由少數人維護
];
錯誤規則化的節奏
  1. 糾正 Agent 的一個 UI 錯誤。
  2. 問：能用 Lint、型別、測試、依賴邊界擋住嗎？
  3. 能 → 請 Agent 寫規則，錯誤訊息附「正確寫法」，並先在原本的錯誤程式碼上報紅。
  4. 真的不能 → 才寫進 AGENTS.md。
  5. 同一個錯出現第二次才立規則（避免把隨口一次的糾正過度外推）。
UI 類常見可規則化項目
  • 業務碼的 useEffect／setTimeout／setInterval
  • 直接操作 DOM（document.querySelector）
  • 互動元素缺少無障礙名稱（同時讓 getByRole 找得到）
  • renderer 引入 main 進程模組（依賴圖邊界）
  • 辯護型註解：「暫時」「workaround」「先這樣」
  • 新增 UI 檔案但沒有對應的 flows/*.json（自訂腳本檢查）
